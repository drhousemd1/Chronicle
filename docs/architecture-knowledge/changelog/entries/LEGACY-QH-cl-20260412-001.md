  problem: The App Architecture page's relationship layer was still vulnerable to false positives because its generator scanned raw file text with regex patterns. That meant markdown code snippets, change-log strings, and other prose-like content could be mistaken for real imports or backend calls. In practice, this produced misleading `Uses`, `Used By`, table, RPC, and edge-function relationships that looked authoritative on the page but were not always true runtime links.
  plan: Replace the regex-based relationship extraction with real AST parsing for executable JS/TS files, leave prose/config assets relationship-neutral unless they contain actual code, regenerate the architecture analysis outputs, and then verify that the known false positives disappear while real runtime links remain.
  changes: |-
    Completed the relationship-accuracy pass for App Architecture:
    • Updated `refresh-architecture-paths.mjs` to use the TypeScript parser for `.ts`, `.tsx`, `.js`, `.jsx`, and `.mjs` files instead of regex-scanning raw text.
    • Added AST-based extraction for static imports, re-export module specifiers, dynamic imports, Supabase `.from(...)` table calls, `.rpc(...)` calls, `.invoke(...)` edge-function calls, and `.storage.from(...)` bucket references.
    • Limited non-code files such as markdown, HTML, JSON, and other prose/config assets to neutral relationship output so code snippets and changelog text no longer fabricate architecture links.
    • Regenerated `architecture-file-analysis.ts`, `architecture-source-paths.ts`, and related generated data so the App Architecture page now drops false relationships from transfer docs and Quality Hub text while gaining more accurate real links like RPC usage and edge-function calls from executable files.
    • Verified that previously misleading examples were corrected, including markdown docs no longer appearing to import runtime files and `ui-audit-findings.ts` no longer claiming fake table/edge-function dependencies from change-log strings.
