  problem: Chronicle's persistence layer was concentrated inside `src/services/supabase-data.ts`, which had become a large mixed-responsibility service handling scenario CRUD, character mapping, conversation/session state, memories, side characters, media uploads, backgrounds, and app settings. That made even safe maintenance work harder than it should be because one persistence change meant reopening a giant file that touched unrelated data contracts. It also made the App Architecture page less truthful once the refactor-planning pass started flagging that file as overloaded.
  plan: "Perform a code-only split with zero backend changes: move the existing logic into domain-focused persistence modules, keep `src/services/supabase-data.ts` as a stable re-export wrapper so the rest of the app does not need a broad import rewrite yet, then refresh the architecture inventory and remove the stale App Architecture warning that still described `supabase-data.ts` as the giant control-center file."
  changes: |-
    Completed Phase 1 of the persistence refactor:
    • Created focused domain modules under `src/services/persistence/` for shared converters, main-character mapping, scenario persistence, conversations/session state/memories, side characters, content themes, and media/settings/background helpers.
    • Replaced the old 2k-line `src/services/supabase-data.ts` implementation with a compatibility barrel that re-exports the new modules, so every existing importer continues to work without a risky app-wide rewrite.
    • Kept this phase strictly code-only: no tables changed, no columns changed, no RPCs changed, no storage buckets changed, and no Lovable migration step was required.
    • Refreshed the generated App Architecture inventories so the page now shows the new persistence module ownership and updated line counts.
    • Removed the stale App Architecture refactor note that still treated `supabase-data.ts` as the large overloaded file, since that warning is no longer true after the split.
