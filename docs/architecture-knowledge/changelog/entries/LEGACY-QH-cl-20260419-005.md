  problem: The API Inspector's slate-blue card badges were still reading as wrong because the measurement logic was not respecting ownership boundaries. Some cards had been showing repeated whole-file totals, and the next pass overcorrected by summing every numeric line reference attached to an item even when the card was rendered inside one specific file lane. That meant a card could sit under one orange file row while its badge math was still influenced by refs from other files.
  plan: "Make the badge logic follow the same ownership principle the App Architecture page uses: a rendered unit should only expose metrics that belong to its own owning file context. For API Inspector cards, that means measuring only the numeric line ranges that belong to the lane file the card is rendered under, and hiding the badge when the mapped source has no trustworthy numeric range to count."
  changes: |-
    Completed the badge-ownership correction pass:
    • Reworked `api-inspector.tsx` so `getItemReferencedLineCount()` now accepts the owning lane path and filters file refs to that path before calculating any line spans.
    • Stopped the badge system from mixing cross-file refs into one visible counter, which removed the misleading duplicated giant totals that were reading like broken per-card measurements.
    • Preserved count-only chip styling from the approved mockup while making the tooltip/title explicitly reflect the lane file the count came from.
    • Hid badges for cards whose mapped refs do not contain a trustworthy numeric line span instead of falling back to misleading whole-file totals.
    • Added singular/plural formatting polish so the UI now renders `1 line` instead of `1 lines`.
    • Revalidated with `npm run ship-check` and a live browser DOM check confirming the first rendered cards now resolve to lane-owned counts such as `1 line`, `87 lines`, `12 lines`, `44 lines`, and `121 lines`.
