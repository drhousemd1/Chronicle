# Chronicle project references

For product orientation when requested, use `chronicle-onboarding`. The Knowledge Base's section registry is `docs/architecture-knowledge/manifest.json`; consult the relevant product documentation and current source for the assigned task. Global working preferences apply.

For UI design or styling, use the relevant region in the **Chronicle UI Guide**. `docs/ui-guide/README.md` explains how to retrieve its Markdown and images directly for a coding task.

When investigating Chronicle implementation owners, dependencies, or handoffs, inspect the relevant Graphify nodes and relationships alongside the written architecture and actual source. A status check or non-rendering map does not count as inspection. Follow **Graphify Access for Agents** in `docs/architecture-knowledge/knowledge-base-system.md` for direct data access and recovery. If the browser map fails, read the same current graph through the command line; report the rendering failure separately. If graph data remains unavailable after the relevant recovery attempt, report the exact blocker and pause graph-dependent conclusions rather than silently skipping it. Give subagents doing this investigation the same access instructions and require the graph ID plus the relevant nodes/relationships actually inspected in their return. After work changes the mapped source or final Git state, check freshness once and refresh if needed before handoff; share one refresh across helpers rather than rebuilding per file or per subagent. A simple text or formatting edit does not require an architecture investigation.

Current Work is retired. Records under `docs/current-work/` are historical reference, not active assignments or workflow instructions. Record Issues and meaningful completed changes independently when relevant; finding an issue does not automatically start a project.

After completing and verifying a meaningful Chronicle change, record one concise entry in the canonical Changelog: what changed, why, and the verified result, including any important limit. Group related work from the same assignment; do not log intermediate steps, routine test runs, record maintenance, or whitespace-only edits. Reuse an existing entry when it already records the same completed change. Use the existing `knowledge:records` accepted-update command for new entries; it does not require a project. For a tracked Issue, cite its ID in the change narrative and put the Changelog ID in the Issue's Resolution before marking it resolved. The Issues tab displays only unresolved findings and is blank when none remain; resolved source records are historical evidence, not pending work. Use the verification already performed for the change rather than starting another audit or test cycle for the log.
